# 异常与回滚手册

> 适用：任务台账系统 · 与《分配规则》配套 · 台账数据：data/tasks.json（原子写 + backups 备份）

## 1. 负责人无响应

**判定**：任务 `in_progress` 超过截止日 48 小时无状态更新。
**步骤**：
1. 看板负载页确认该负责人"逾期"数（逾期任务整行标红）；
2. `PATCH /api/tasks/{id}`：`status=blocked`，note 写明"负责人无响应，暂挂"；
3. 改派：`PATCH` 指派到新负责人（或退回 `pending` 重新指派），history 记录改派链；
4. 若改派到人不确定 → 通知用户裁决（规则 §5）。

## 2. 指派错误

**场景**：任务指给了错误的人/角色。
**步骤（按影响面）**：
1. 单条：直接 `PATCH` 改派到正确负责人（history 自动留痕"改派→X"）；
2. 需要恢复全貌：`POST /api/tasks/{id}/undo` 撤销最近一次变更（恢复快照 + 追加撤销记录）；
3. 多级错误：连续多次 undo 逐级回退，每次都留痕。

## 3. 批量分配错误 / 台账损坏

**步骤**：
1. 停写（避免覆盖好数据）；
2. 恢复备份：`copy data\backups\tasks-<时间戳>.json data\tasks.json`（原子写保证覆盖瞬时不半态）；
3. 服务热读无需重启，GET /api/tasks 核对恢复结果；
4. 差异处理：备份点之后产生的合法任务重建（source 字段可追溯）。

## 4. 任务积压

**信号**：负载页某负责人"未完"占比 >80% 且 P1 >2。
**步骤**：用户裁决拆分或降级——拆出的子任务 source 写"从 TASK-xxx 拆分"；降级注明原因。

## 5. 台账文件损坏（已被服务防御）

服务对损坏 JSON 返回 500 并指明用 backups 恢复，**不会静默清空**；按 §3 恢复。

## 6. 撤销纪律

- undo 只回退最近一次变更；连续 undo 逐级回退；
- 撤销记录本身不可被"再撤销"（防循环），回退到指定历史点请用备份恢复。
