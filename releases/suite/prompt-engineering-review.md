材料：pm/prompts.py（589 行，6 节点 SYSTEM+RULES，v3 已四轮迭代）+ 会审台 REVIEW_SYSTEM + pe-baseline.json / pe-ab-test.json 实测

## 一、总评：87/100（这套提示词在同类中属于前 10% 水平）

作为提示词工程师，这个项目的提示词资产质量明显高于我预期的"演示项目"水准。给出三个硬证据：

1. **结构纪律满分**：XML 标签隔离外部内容（防提示词注入劫持，标注 M6 定界符越界修复）、system/user 切分、structured output 走 Pydantic schema、`<<VAR>>` 占位符避开花括号冲突——这些是生产级提示词的标配，多数团队连第一条都做不到。
2. **迭代方法论教科书级**：prompts.py 头部 17 条修复日志不是装饰，每条都能对应实测：第 11 条"字段声明顺序=自回归生成顺序"（issues 在 scores 前面，否则模型先给数再编证据）这是深刻的 LLM 生成机制理解；第 17 条"同一规则必须配反向护栏"+"验证结果：第一形落地 Δ+2.80→+0.35，第二形没落地"——**承认锚定失败而不假装成功**，这个诚实度超过 90% 的生产系统。
3. **rubric_stamp 缓存指纹**：评分提示词一改，旧评估缓存自动失效（防"拿上一版标准的结果汇报这一版"）。这是把提示词当版本化资产管理，绝大多数项目没有。

## 二、实测：会审台 REVIEW_SYSTEM A/B（4 真实任务 × 2 版提示词）

| 任务 | V1 现行版 | V2 锚点版（我写的） | 结论 |
|---|---|---|---|
| T1 混合 | billing/P2/0.95 ✅ | billing/P2/0.92 ✅ | 平手 |
| T2 已扣款无订单 | billing/**P2**/0.85 ❌ 严重度误判（资金损失应为 P1） | billing/**P1**/0.9 ✅ action 给出流水核查+补单具体路径 | **V2 胜** |
| T3 "帮我看看" | other/P3/0.6（过度自信） | **JSON 跑飞**（约束过载） | **V1 胜** |
| T4 生产故障 | technical/P1/0.95 ✅ | technical/P1/0.95 ✅ | 平手 |

**JSON 合规率**：V1 = 4/4 raw-ok（与生产 parse 记录一致）；V2 = 3/4（T3 跑飞）。
**基线 JSON 合规率 100%** 说明 parse_verdict 的多层容错（剥围栏+正则提取）是保险丝而非常态依赖——提示词本身够硬。

## 三、核心发现（A/B 的教训比成功更有价值）

1. **锚点有效但有代价**：V2 的 severity 三档口径（P1=资金损失/生产故障/舆情正在发生）修正了 T2 的真实误判——这是明确的增益。
2. **弱信号场景是锚点的天敌**：V2 给 T3 堆了弱信号规则+置信度锚点+action 约束三层要求，模型在"几乎无信息"输入上试图同时满足全部约束，直接 JSON 跑飞。**结论：约束数量与输入信息量成正比地压垮模型**。
3. **正确定稿是混合策略**：severity 口径+action 可执行性（对强信号有效）保留在 system；置信度锚点压缩为单行；弱信号指令移到 user 段（跟随工单内容注入，只在检测到短正文时出现）。

## 四、定稿建议（可直接采纳）

```python
REVIEW_SYSTEM_V3 = (
    V1 保留全部
    + " severity 口径：P1=资金损失/生产故障/舆情正在发生；P2=功能受损但有替代路径；P3=咨询/轻微不便。"
    + " action 必须是客服可直接执行的下一步（含时限或对象），不许写\"尽快处理\"。"
    + " confidence 锚点：0.9+=诉求明确；0.7~0.8=主题明确缺关键细节；≤0.6=信息不足以分类。"
)
# user 段追加（仅当正文 <30 字）：
# "（弱信号工单：category 取 other、confidence ≤0.5、action 写向客户澄清的具体问题）"
```
