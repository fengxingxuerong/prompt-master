## 二、改了什么（按"会不会骗到人"排序）

### 会骗到人的（最该修的）

1. **评估缓存键缺评委指纹**：换端点/温度/max_tokens 都不让缓存失效 ⇒ 报告拿旧评委的分
   冒充新读数。改用 `call_fingerprint`（代价是存量评估缓存一次性失效，刻意选择）。
2. **空产出封顶四连错**：`"42"`/`"YES"` 这类正确答案被判空壳封顶 4.0；封顶取错采样；
   `passed` 不同步（报告并排「通过 1」与「未达标」）；基线臂不走封顶 ⇒ 两臂不同口径、**Δ 反向**。
3. **注入门禁粘滞**：修好注入缺陷的那一轮，报告首行仍印「未达标·门禁拦截」。
4. **报告印的阈值 ≠ 判定用的阈值**：能印出「✅ 达标：均分 7.8 ≥ 阈值 8.0」这种假命题。
5. **`history` 的「✅ 显著」43% 是算出来的**：小样本用 1.96（大样本分位）⇒ 换 t 分位、
   `var=0` 判"不可判"、被丢掉的组不再整组消失。**本机账本实测 7 组翻 3 组。**
6. **合规片段永远拿不到否决权**：`expected` 含「不得」就被判成需求规则、预检直接拦下 ⇒
   这类用例根本没法表达。新增 `"literal": true` 显式开关（不做第二层启发式：真实语料里
   「必须包含3条结论」与「不得对外担保」长度相同、语义相反）。

### 零调用层（用户可见收益最大）

约束预算闸对 `**约束**` / `【约束】` / 裸 `约束：` / `Rules:` / `(1)` / `①` 整类失效 ——
一份 12 条硬约束的提示词曾拿到"未命中任何确定性规则"、**退出码 0**。
端到端：现在同一份从「0 条 / exit 0」变成「12 条 + `constraint_overload` / exit 1」。

### 可靠性 / 资源

限流器字典无界、`_futures` 只增不删、SSE 断流泄漏线程与 socket、`PM_API_TOKEN` 明文进日志、
`PMH_TIMEOUT=60s` 让流式全 500、校准账本损坏后被"当空账本"整份重写、存储两后端语义分叉
（`evict(0)`/并发写丢字段）、Windows 上 `subprocess(text=True)` 用 cp936 解码 UTF-8 ⇒ 断言假绿。

### 用量与成本

「重试请求数」恒为 0（`add_retry_request` 零生产调用点）→ 接通四个重试点；
流式调用不进 `/v1/usage` 日聚合；成本段声明"只按成功调用折算"；新增 `PM_MAX_LLM_REQUESTS`
（真实请求数），**不动**老开关 `PM_MAX_LLM_CALLS` 的语义。

### 前端 / 面板 / 桌面

历史面板与三套发布服务的页面把**用户可写字段**裸拼 `innerHTML`（存储型 XSS，四处）；
成本看板 `startLive` 写在文档结束标签之后 ⇒ 打开即"加载失败"且归因错误；
面板判决色与 CLI 退出码相反（绿"ok"而 CLI 是 exit 1）；桌面"只读扫描"会重写 `.git/index`。

### 发布套件（`releases/`，此前只被 CI 跑测试、从未语义审计）

跨进程丢单（全量 `DELETE`+re-INSERT + 进程内锁）→ 照 triage 范式改成 `BEGIN IMMEDIATE` +
只写自己那一条；开 token 后四页把 401 画成"暂无数据"（用空集冒充没数据）；
通知中心 `count` 硬编码 0；撤销连按两次只回滚一步却每次报成功；
`PATCH due` 绕过校验导致逾期恒 0；watchdog/monitor 只看 HTTP 200（存储坏了仍报绿）、
探针不带令牌、台账轮转路径写死且失败被吞。

### 文档

11 处文档与真实行为不一致（`--task "..."` 照抄即退 2、`--fast` 是 12-22 次不是 8-10、
MCP 工具数、`.env` 默认值、已拆分的模块路径…）。`docs/evaluation.md` 新增 §三十五，
逐条核过历史"显著"结论在新口径下**都没翻转**（只变宽不变结论），所以历史记录保持原样。

## 三、凭什么说改对了

- **每条修复都带回归用例**，其中 **8 处做过变异验证**（把修复撤掉，断言必须当场红）：
  SSE 断流清理、探针队列有界、流式入账、`literal` 透传、死常量守卫、只读扫描、
  releases 的 XSS 守卫、监控的存储判据。
- **差分判据**取代"各测各的"：`watchdog` 与 `monitor` 对同一批输入必须给同一个答案；
  面板读数与当场 CLI 读数逐字段相等；`has_assertion` 与执行器 `check_assertion` 同源。
- **项目自己的门禁全过**：pytest / ruff / ruff format --check / mypy strict / 覆盖率地板 /
  复杂度棘轮 / `run.py gate` / 拓扑自检 / 运营数据未被写脏。
- 变异验证本身踩过一个坑并记了下来：第一次给"死常量守卫"做变异时 PowerShell 把转义序列
  当字面量写进文件，源码坏掉后被判据的 `except SyntaxError: continue` 跳过 ——
  **"跳过解析失败的文件"是这类守卫的天生漏洞**，变异必须改出一个语法合法的反例。

## 四、还剩什么

- **本产品侧：无「已知未修」。** 判定链上还剩两个纯口径选择（是否把
  `PM_MAX_LLM_CALLS` 的计量也改成请求数、是否收紧 advisory 降级），已记录为所有者决定。
- **`releases/` 侧**：只剩体检工具自身的读数问题（`five_dim_audit` 一条固定误报、
  `smoke_suite` 自称三服务却不含 triage），不影响服务运行。
