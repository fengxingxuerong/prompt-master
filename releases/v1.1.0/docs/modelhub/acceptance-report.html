04自动切换实证

切换不需要人工介入，两类真实场景均留有台账记录（request_id 可在 logs/modelhub_ledger.jsonl 检索复核）。

场景 D：强制指定已知不可用模型（端到端测试）

t=0s
请求 model=amd-glm-5.3-flash
该模型当前读超时（已知不可用）
t+45s
45s 快速超时触发 → 切换（reason: timeout）
t+46s
尝试 deepseek-v4-flash，遇商汤限流 → 再切换（reason: rate_limited）
t+48.5s
glm-5.2 成功返回，对话结果正常；全程 failovers=2，request_id d48c485a65c6

场景 B（附带）：真实限流切换（CLI ping 期间）

03:29:26Z
deepseek-v4-pro 请求遇 HTTP 429（tpm/rpm limit，code 429005）→ 切 deepseek-v4-flash
03:29:27Z
deepseek-v4-flash 也 429（code 429003）→ 切 glm-5.2
03:29:29Z
glm-5.2 成功（2.8s）；request_id c977161cb5f1

切换触发条件覆盖：连接错误、读超时、HTTP 401/403/404/429/5xx、200 空返回（假成功）。同一模型连续失败 3 次进入 300s 冷却（可配），冷却到期自动放行自愈。

05角色设定固定不漂移

10 个角色（clarifier / optimizer / evaluator / evaluator_b / arbiter / comparator / reviser / target / assistant / analyst）的系统提示词固定存于 config/roles.json，与模型完全解耦：网关在请求进入时按 role 注入 system 消息，切换到哪个模型都注入同一份人设。

实测（场景 E）：同一 role=analyst 分别经 deepseek-v4-flash 与 glm-5.2 对话"你的角色设定是什么"，两个模型都准确复述同一人设——"严谨的数据分析师，先给结论、再给依据与计算过程，数据缺失明确说明、不编造数字"。人设随角色走、不随模型漂移，验证通过。

角色文件支持热重载与版本管理（存于项目 git 忽略之外的 config/ 目录，改动留 mtime 与备份可溯）；引用不存在角色时 HTTP 422 显式报错并列出可用角色，杜绝静默空人设。

07调用与切换台账

每次真实调用与每次切换均追加写入 logs/modelhub_ledger.jsonl（JSONL，一行一事件，并发安全）。事件字段含：时间戳（UTC ms）、类型（call/switch）、request_id、模型、端点、成败、耗时、尝试次数、切换次数、HTTP 状态、错误类型与摘要、agent、role、正文长度。

检索能力实测：最终回归时点台账累计 80 条事件（36 次调用 + 44 次切换），按模型 / 成败 / 类型 / 时间窗 / request_id 六个维度检索均可用（CLI ledger 与网关 GET /v1/ledger 同源）。汇总视图（stats）给出总调用、成功率、切换次数与按模型分布。

注：切换事件数（44）大于触发切换的调用数属预期——多跳切换（如 429 连续两跳）每次跳转记一条；被网关层 422/400 拒绝的异常请求不计入调用事件，同样属设计语义。
