# 任务分配规则

> 版本 1.0 · 适用：本任务台账系统（2–10 人或执行角色）· 最终确认人：用户

## 1. 谁能做什么

| 角色 | 建任务 | 指派 | 更新状态 | 撤销 | 裁决冲突 |
|---|---|---|---|---|---|
| 用户（最终确认人） | ✓ | ✓ | ✓ | ✓ | ✓（最终裁决） |
| Agent-AutoClaw（执行代理） | ✓ | ✓（「待定负责人」除外） | ✓ | ✓ | ✗ |
| 其他成员（未来加入） | ✓ | ✗（只能认领空指派任务） | 仅自己的任务 | ✗ | ✗ |

**「待定负责人」是占位角色**：API 层禁止指派到该角色（422）。要真指派给人，先由用户确认真人姓名并加入花名册。

## 2. 任务从哪来（来源必填）

每条任务创建时**必须填写 `source`（来源）**，保证可追溯：
- 文档遗留清单（如验收报告的"遗留风险与建议"）
- 会议/沟通决议（写明日期与一句话依据）
- 用户口头指令（写"用户 2026-09-21 指示"）

来源为空的任务拒绝创建——这是防"虚构任务"的硬闸。

## 3. 优先级与截止日期怎么定

| 优先级 | 含义 | 默认截止 |
|---|---|---|
| P1 | 阻塞他人或临近期限的高压任务 | 3 天 |
| P2 | 常规推进任务（默认） | 7 天 |
| P3 | 可以排队的改进任务 | 21 天 |

- 截止日期可显式指定，空则按优先级自动推算；
- **P1 与跨人改派需用户确认**（规则冲突裁决权在最终确认人）；
- 逾期任务在看板整行标红，并计入负责人负载的"逾期"数。

## 4. 状态机

```
pending（待处理）→ in_progress（进行中）→ review（待复核）→ done（已完成）
       ↘ cancelled（已取消，需注明原因）
in_progress ↘ blocked（阻塞，注明阻塞原因；解除后回 in_progress）
```

- `review` → `done` 只能由用户（或任务指定的验收人）操作；
- `cancelled` 与 `done` 是终态，进终态后如需返工，创建新任务并在 source 里引用旧编号。

## 5. 冲突如何裁决

1. **负责人冲突**（两人都认为任务归自己/都不认）：由用户裁决，裁决后改派一次到位，history 留痕；
2. **优先级冲突**（两个 P1 抢同一资源）：用户按"阻塞面大小"排序，必要时把其中一个降到 P2 并注明原因；
3. **执行代理自动指派的任务**：用户保有随时改派与撤销权（undo 一键回滚）。

## 6. 撤销（undo）

任何一次变更（创建/改派/状态/优先级）都可撤销：看板上每个任务行都有「撤销」按钮，或 `POST /api/tasks/{id}/undo`。
撤销 = 恢复到最近一次变更前快照，并**追加一条"撤销"记录**——台账永远保留撤销痕迹，不做物理删除。
