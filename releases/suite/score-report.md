## 二、分项得分

### A 功能完成度：88/100（权重 30% → 26.4）
**加分证据**：
- 四服务全部在线且核心路径实测通（C1-C14 探针 14/14 PASS）
- 15 模型池 5 路上游自动调度+熔断（C2 真实调用 6.4s 正常）
- 会审台全链路异步化（提交 31ms，SSE 逐票实时，wait=1 向后兼容）
- 成本看板/通知中心/超时提醒/回滚手册齐备

**扣分**：
- −7：OpenRouter 通道 402 跑不通（占 5 路上游的 1 路）
- −3：龙虾站内容仍为占位口径（演示可用，对外不可）
- −2：流式转发部分可用（TASK-002 等商汤口径）

### B 技术质量：90/100（权重 25% → 22.5）
**加分证据**：
- 705 自动化用例全绿（main 688 + lobster 7 + triage 10），三轮独立回归复核
- 性能基线 17 端点全 <30ms；唯一结构性热点（ledger 全量解析）已优化消除增长斜率
- 缺陷密度：当日新发现 4 个（D-011~D-014）全部处置闭环，无高危遗留

**扣分**：
- −5：D-013 暴露多实例并发写无防护（sessions.json 被覆盖，靠 git 快照恢复）——单实例纪律是约定而非机制保证
- −3：D-014 stderr 噪音（langgraph 后台任务清理竞争，scheduler 无生命周期钩子）
- −2：写放大未处理（save_sessions 全量写，100 会话预估 ~50ms）

### C 产品价值：82/100（权重 20% → 16.4）
**加分证据**：
- 解决真实问题：多 LLM 调用的容灾/调度/审计一站式（对接方只需一个 URL）
- 会审台是可直接使用的完整范式（工单→研判→共识→反馈），非 demo
- 任务台账+成本看板+运维自动化形成管理闭环

**扣分**：
- −10：无鉴权与多租户（安全豁免期约定），限本机/可信环境使用，对外需先解除豁免
- −5：单机 JSON 存储，数据规模化受限（100 会话/千条任务为实际天花板）
- −3：通知仅落盘+自备 webhook，无开箱即用的 IM 推送

### D 工程纪律与可维护性：93/100（权重 15% → 13.95）
**加分证据**：
- git 4 个 tag 锚点（v1.4.0~v1.4.3），今日 11 次提交全部留痕
- 文档资产：根 README + 各服务 README + 13 md + 13 html 报告；接手人无需口头背景
- 回滚体系：triage 五代 .bak + git tag 双轨，回滚演练实测 8.5s/7.8s
- D-013 事故 3 分钟从 git 快照恢复——留痕体系实战有效

**扣分**：
- −4：修复用 .bak 文件与 git 并存（双轨冗余，历史上版本管理断档的补救痕迹）
- −3：部分测试断言耦合版本号（v1.1.1 写死导致误报，已修但模式需警惕）

### E 创新性：86/100（权重 10% → 8.6）
**加分证据**：
- majority-return 提前汇总 + late 票机制：不阻塞主流程的多评委协作形态
- 评委健康度滑动窗口 + 座位级抖动（PM_JUDGE_JITTER 进不确定度与仲裁线）：把校准数据真正用进调度
- 坏模型名 0.03s 快失败（白名单前置）：网关层的防御性设计

**扣分**：
- −8：核心范式（多模型并行+共识）业界有同类，差异化在工程细节而非范式创新
- −6：无自主创新的评测方法论输出（校准/仲裁思路来自通用实践）

**信息不足标注**：无——全部维度均有当日实测材料支撑，无需区间估计。
