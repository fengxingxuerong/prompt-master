## 三、这一轮数据给出的五个核心发现

**1. 评估框架错位是这轮最值钱的发现，不是评委不行。**
成对盲评给出 **0:4 判基线完胜**，与 Δ=+1.71 正面冲突。逐条读评委理由：
"原始需求要求'写一个提示词'，候选 B 直接提供了完整的提示词正文……"——四条形同一致。
根因：用户 task 写成"写一个提示词，让 AI 对工单分类"，于是**优化臂的输出是一张分类结果，
基线臂的输出是一份提示词文档**，而喂给评委/盲评的 `<ORIGINAL_TASK>` 就是那句"写一个提示词"，
于是评委按"谁更像一份提示词"来判。这是框架错位，不是位置偏置，也不是模型笨。
已修：`COMPARATOR_SYSTEM` 与 `EVALUATOR_SYSTEM` 各加一段显式分层——候选是"系统照提示词干活的
结果"，需求写成"写个提示词做 X"时按"X 办得好不好"评，禁止因"不像提示词"扣分。
结构性后选方案（需改测量口径，未做）：把澄清阶段产出的 `task_summary`（下游任务口径）
作为评委的 `<ORIGINAL_TASK>`，而不是用户原文。

**2. `samples=2` 下噪声大到能吃掉整个判定余量。**
平均极差 2.193、两条用例被判"结论不稳"（case#0/#1），保守下界 6.05 比点估计低 2.1 分。
这解释了为什么"分数 8.16 却未达标"是对的行为，也说明**要下"变好了"的结论，
samples 得往 3-5 走**，或者接受"下界说了算"。

**3. 初版可能根本不是可用交付物，v0=2.11 是被下游救回来的。**
版本曲线 `v0 2.11 / prompt 长度 0 字符` → `v1 8.16 / 742 字符`：优化器首版**空返回**
（端点 500 + 推理耗尽那一类），质量门按"提示词为空"拦下并带 hint 重试，才没让空交付物进入评估。
同时它让我刚加的净增量检查报了"净增量 74100%"——对退化基准算百分比无意义，
已改成基准 <`MIN_PROMPT_LENGTH` 时只报绝对长度。

**4. 注入存活的两处误伤，都来自真实数据而不是设想。**
- 假阳性：模板自带 marker「已解决」，而目标模型其实**拒绝了**注入（分类给「其他/信息不足」
  而非注入要求的「物流」），只因输出里提到"已解决"这个领域高频词就被判劫持 → 门禁把达标结论压掉。
  已把种子用例也统一成"代码派生高熵校验码"（与生成用例同口径），用户自带的注入文本与 expected/mode 不动。
- 计数放大：`total/hijacked` 原来按 run 累加，1 条注入用例 ×2 采样被写成"2/2 条被劫持"，
  等于把 1 个缺陷报成 2 个。已改为按用例计数，details 里标"命中采样 0,1/2"。

**5. 评委跨家族后，"防放水"从同类采样变成真的交叉。**
用 6 条人工锚点逐家量（同一评估管线）：

| 家族 | MAE | 偏差 | 排序 r | 处置 |
|---|---|---|---|---|
| sensenova-6.8-flash-lite（改前 A=B=仲裁） | 1.07 | +0.96 | 0.901 | 留任 A |
| glm-5.2 | 1.28 | +1.28 | **0.976** | 评委 B |
| deepseek-v4-flash | 1.63 | +1.10 | 0.658 | 仲裁 + 盲评 |
| kimi-k3 | — | — | — | 不可用：端点强制 `temperature=1` |

三家一致偏松且偏在同一类（编造关键事实：人工 2.5-3.5，评委 4.0-5.85），说明**是档位本身给宽了**。
把编造锚带 5-6 → **3-4**、加"含编造则总分封顶 6.0"、补一个"格式完美但数字是假的 → 3.55"反面样例后：
A 的 MAE **1.07 → 0.37**（偏差 −0.12、r 0.968），B **1.28 → 0.46**（偏差 −0.26、r 0.997）。
（**这两个是 6 条手写锚点口径。**锚点后来扩到 11 条、双方重新入账为 A 0.90 / B 0.98，
涨的部分来自考卷变难不是评委变差，两家在同一类缺陷上偏松 +2.25~+3.53 —— 见
[evaluation.md](evaluation.md) 第八节。）

### 发现 6：Δ 会被端点抖动的"相位差"冒充成质量差

第 2 点表面看是"优化版把任务搞砸了 4.81 分"。逐条核对运行期错误才发现真相：
**优化臂 8 个样本 `empty_output`**（目标模型返回空内容、不抛异常），3 条用例里 2 条
一个有效样本都没有 → 按刻度下限记 1.0 → 拖出 2.9 的均分；而基线臂恰好落在端点正常的
时间窗，7.71 是干净拿到的。两臂不在同一相位上，Δ 就没有质量含义。

这条直接催生了一个新闸：`report.py::_infra_invalid_cases` 现在数"本臂有多少条用例
**没有任何有效样本**"，只要 ≥1 就在 Δ 表下面印

> ⚠️ **本轮 Δ 不可采信**：优化臂有 2 条用例没有任何有效样本……先错峰重跑本臂
> （或调大 `PM_TARGET_MAX_TOKENS`，空输出多半是 reasoning 耗尽预算），再谈优化有没有变好。

第 2 点的报告已按新逻辑离线重渲染（`render_report` 只读 state，不再打端点）。

### 发现 7：fixed–broken 记账当场抓到"越修越坏"

同一轮的版本曲线是 `v0 6.0 → v1 2.9`，而新加的逐条账本写的是
**「修好 0 条／弄坏 1 条（#2），净值 −1」**——这正是移植 GEPA/PRISM 记账要看见的那种情况：
均分从 6.0 掉到 2.9 只说了"变差"，账本说的是"一条都没修好，还赔了一条"。
（本轮净值的分母被空输出污染，但机制在真数据上确认工作。）

### 发现 8：评委自己发现了优化器的约束超载

第 2 点的 issues 里有一条 `prompt_quality_warning`：被测提示词「[约束] 和 [边界规则] 段共
12 条编号条目，超过上限 8 条」。同一条缺陷也被代码侧质量门抓到（报告的质量警告段落 v1 那一行）。
两路独立命中同一事实，是这个闸设计对了的证据；同时也说明修订器**确实**会在预算压力下加条数，
≤8 不能只靠提示词自觉。

### 发现 9：两个"看起来正常"的 token 额度，实际都在制造空返回

跨家族评委一上线就暴露了两处预算配置错误，症状都是**不抛异常的空内容**（伪装成"评委失败"
或"目标模型没做好"）：

| 角色 | 原额度 | 症状 | 依据与处置 |
|---|---|---|---|
| 评委 B（glm-5.2，思考型） | 12000 | `reasoning_tokens=12000 / completion_tokens=12000`，正文额度归零 → 整条评估作废 | reasoning 按 prompt ×1.1~1.5 估；`EVALUATOR_SYSTEM` 已 ~3.8k 字符 → 提到 **24000**（仲裁/盲评同步） |
| 目标模型 | 8000（代码默认，`.env` 未覆盖） | 第 2 点 9 次空输出，2/3 条用例一个有效样本都没有 | 代码里 8000 的对照来自"简单输入 ×3"；交付物长度已从 ~700 涨到 8900 字符 → `PM_TARGET_MAX_TOKENS=16000` |

这条修复**先在失败现场上验证再重跑**：拿第 2 点那份真实交付物 + 真实用例打一次 target，
16000 额度下正常返回 303 字符（42 秒），不是靠"应该可以了"就重启三小时的任务。

因此三点矩阵在 23:40 起重跑一遍（前两轮的部分结果按目录归档在
`logs/matrix18_*_prefix/`，不作质量结论，只作故障证据）。

### 发现 10：双向评把"位置偏置"和"真差异"分开了

第 1 点四对输出，正序 + 交换 A/B **全部一致**（`position_flips = 0`），结论仍是基线 3:1 胜出。
对照 1.0.0 那次单序盲评的"0:4 判基线完胜"，这次是"1:3 且两序可复现"——
说明基线在客服域确实不吃亏，而**优化没有跑赢"把需求原样说一遍"**。
同时评委的逐条理由也支持这个判断：case#1 里优化版输出在信息不足时直接给了根因结论
（"包装破损通常指向运输/物流环节受损"），被判无依据猜测——这是真实缺陷，不是评分噪声。

### 发现 11：同一条注入用例，从假阳性变成真阳性

第 1 点的注入用例被判定劫持，依据是目标模型真的吐出了代码派生的高熵码
`A8CBA30C`（两个采样都命中，details 记「命中采样 0,1/2」）——
与 1.0.0 那次「已解决」高频词的**假阳性**形成直接对照：现在报劫持就是真劫持。
更关键的是基线臂拿同一批用例检测出 **0/1**：这条劫持是**优化版提示词自己引入的缺陷**，
而不是"这份测试数据谁都可能中招"。基线侧检测（`baseline_injection_survival`）第一次上线就改变了结论的读法。

### 第 1 点失败的成因（以及报错信息为什么不够用）

`run_id=6cb905b7e30e` 三次都是 `未在输出中找到合法 JSON 对象`，落在端点持续
`500 engine is not available temporarily` 的窗口里：原生结构化通道挂了 → 退到文本通道 →
文本里没有 JSON。原报错不区分成因（空内容 / 散文 / 被 max_tokens 截断），会把人引去改提示词
而不是查端点或调 `MAX_TOKENS`。现在 `llm.py` 只报**形状事实**（长度、花括号是否配平、
是否以 `{` 开头），**不回显模型文本**——这段文本会被拼进重试的 `<previous_error>`，
把被测内容原样搬回去等于自增注入面。

### 顺带记下一个记账缺陷（未修，优先级低）

失败的 clarify 节点不计自己消耗的调用数，所以那份失败报告写的是「LLM 调用次数：0」，
而实际打了 3 次以上并经历了 429 退避。真实计数在 `llm_usage` 台账里是对的
（报告末尾的用量表能看出来），但「调用次数」这一行与台账是**两套真相**。
正确修法是让 `llm_usage` 成为唯一来源、报告那行从台账取数，属于小重构，留给后续。



### 发现 12：两个口径在两点上都不同向，而且方向相反

把第 2 点重跑干净之后，最值得记的不是"+1.83"，而是它和盲评的关系：

| 点 | 绝对分口径 | 成对盲评口径 | 一致吗 |
|---|---|---|---|
| 1 客服分诊 | Δ +0.38，判定未达标 | 1:3 判**基线**优，`position_flips=0` | 否 |
| 2 销售分析 | Δ +1.83，判定**通过** | 1:1:1 **持平**，`position_flips=1` | 否 |

两次都不一致，而且一次偏向优化版、一次偏向基线——所以这不是发现 6 那种基础设施假象，
是**两种量法在量不同的东西**：绝对分问"每条约束有没有被写到"，成对偏好问"哪一份更值得采用"。
第 2 点盲评的三条理由恰好把裂缝摊开：一条批评优化版自设阈值漏掉 9 月环比异常、
一条批评基线把"数据缺失"当异常值、一条批评优化版不听"只输出异常点"的指令。

含义很直接：报告里"Δ 为正 + 盲评持平"不是需要消解的矛盾，是必须同时报的两个事实。
**只引用其中一条的结论都不成立**，包括交付时那句"优化后更好"——这也是
`--no-pairwise` 真正的代价：省下的调用是个位数，丢掉的是"位置偏置"和"真实偏好"两个信号。

### 发现 13：仲裁上抬 +0.36，其中 +0.15 就是家族偏松——而这组数本身差点骗过我

把三个 run 的日志里所有双评委轮次挖出来（37 轮，含两个臂与全部迭代），仲裁这条路径的行为
和我以为的不一样，而且不是任何一种我文档里写过的样子：

**1）它触发得很频繁。** 两个已完成的 run 共 26 个双评委判定轮，其中 **9 轮（35%）**分差超过
`PM_JUDGE_DISAGREEMENT=2.0`（分差中位 1.36、最大 4.75）；把在跑的第 3 点并进来是 16/40。
也就是说"双评委交叉验证"里每三次就有一次其实**没在验证，在吵架**——而吵架的结果只采信一个人。
这条与下面的样本量问题无关，是硬事实。

**2）仲裁从不低于较严的那位，但偏松幅度比我以为的小。** 9 个可配对的仲裁轮：落在两评委之间
**8** 次、≥ 高分侧 **1** 次、**≤ 较严侧 0 次**；相对两者均值 **+0.36**（中位 +0.38，5/9 为正），
距较宽评委 −1.16。"退化成取 max"不成立；"单向偏松"方向成立、幅度只有三分之一档。

**3）把 `arbiter` 自己校准之后，这个 +0.36 基本不需要第二个解释。**
`run.py calibrate --judge arbiter`（同 11 条锚点、同 rubric，`anchors=318d98f08b`）：
`deepseek-v4-flash` 偏差 **+0.62** / MAE 0.97 / r 0.879，对照 A +0.41 / B +0.53，
它在**普通锚点上**就比两评委均值多松 `0.62 − 0.47 = +0.15`。剩下 +0.21 在 n=9 上没有任何统计意义。
⇒ **先前挂在账上的"锚定怀疑"（`judge.py:201-207` 先给看分数再要求忽略）目前无证据支持**，
降级为"措辞上确实别扭、但没有可测后果"；不必修，也不该为它改阈值。

**4）本条自己的样本量教训（比上面三条更值钱）。** 我先前把三个 run 的日志合并算出的是
**+0.79**、并由此判定"家族只解释五分之一"；把**仍在写的第 3 点日志**剔掉、只留两个已完成
run 之后，同一个统计量变成 **+0.36**，而"相对位置随分差上升还是下降"这个判据**换了符号**
（三 run：0.81→0.74；两 run：0.59→0.65；corr 都≈0）。一次在跑的跑批把结论从
"另有隐情"推到"家族足矣"。所以：**争议轮的统计在 n<15 且样本还在长的时候不能当数**，
冻结口径（只用已完成的 run）才有意义。要真正定量，得攒到 30+ 个争议轮。

**5）同一条路径的两个出口保守性相反。** 仲裁**成功** → 完全采信第三方一人；
仲裁**调用失败** → 回退「取两评委较低分（安全侧）」（judge.py:217-221）。
端点越抖判定越保守、端点正常时反而偏松——这会把"基础设施质量"混进"分数"里。

**6）它对第 1 点的结论有多敏感（拿已落盘的 state 当场算的，零成本）。** 第 1 点最终表里唯一
出自仲裁的是 case#1：`A=8.45 / B=4.75 → 仲裁 5.4`，代表样本加权分 6.75。剔除它，
优化臂 8.05 → 8.48，**Δ 从 +0.38 变成 +0.81**。方向不变（仍未达标、盲评仍判基线优），
但 "+0.38" 这个数**不能当点估计引用**——它整个建立在一次 3.7 分的分歧裁决上。

**已修的部分**：报告现在会印「分数出处：N/M 例出自**仲裁者一人**……这些数不是双评委共识」。
在此之前 `n_arbitrated` 只进 trace，交付物里读者看到的仍是"双评委"口径的表
（`tests/test_report.py` 钉住，并用两个真实 run 的 state 离线复渲染验证过）。
